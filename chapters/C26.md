# 这个项目到底赚不赚钱

一个项目终于上线，客户愿意续约，工程团队也拿到了好评。经营者仍然需要再问一个朴素的问题：为了得到这份收入，我们究竟花了什么？

答案常常散在不同地方。现场工程师算在交付部门，协助排障的产品工程师算在研发，售前试验没有进入合同，客户自己的人员投入更不会出现在供应商账上。若只看合同金额与驻场人数，一个看似赚钱的项目可能一直在向其他团队借资源。

FDE 模式值得认真计算，恰恰因为它同时包含服务、产品学习和长期客户关系。投入有机会在未来复用，也可能变成持续维护的负担。两种结果在项目开始时看起来很相似：都有人忙着解决当前客户的问题。

## 先把三本账放在同一张桌上

第一本是客户的账。新的工作方式节省了什么，增加了什么，是否改善了它真正关心的结果？第二本是供应商的项目账。这次交付的收入能否覆盖为了它发生的成本？第三本是产品的账。项目留下的能力能否帮助其他客户，值得由多少公共研发预算承担？

三本账不能互相冒充。客户节省了时间，不代表供应商盈利；供应商拿到高毛利合同，不代表客户获得了相应价值；一个项目本期亏损，也不能只因团队说“学到很多”就被自动视为成功研发。

C02《Palantir：现场的问题，怎样进入产品》提到，Palantir 的2020年上市文件把客户获取、关系扩展和规模化后的经营分开观察。这里借用的是早期投入与成熟客户应分开分析的问题意识；公司自定指标不能直接当作本章项目账的利润，也不能代表每位 FDE 的独立产出。[^1]

阶段划分不会替任何项目保证结局。是否值得承担早期投入，还要回到可以检查的成本与后续使用。

## 一笔可以逐项检查的项目账

下面全部是假设数字，用于说明算法，不是行业报价、薪酬水平或任何公司的真实合同。假定一家供应商承接一期交付，合同收入80万元，交付范围和收款条件都已明确。为了便于理解，先不考虑税务和收入确认时间差。

三名工程师各投入50个工作日，按每人日3000元的完整人员成本计算，共45万元。这里的人日单价包含工资、雇主承担的福利及相关人员费用，排除下文另列的共享设施和行政费用，不等同员工日工资。另有不在这三人之内的产品支持和客户协调合计25个人日，按2400元计算，为6万元。项目专用云资源和模型调用4万元，差旅及专项审查3万元。

| 一期项目假设 | 金额 |
| --- | --- |
| 合同收入 | 80万元 |
| 三名工程师，共150个人日 | 45万元 |
| 产品支持与客户协调，共25个人日 | 6万元 |
| 云资源与模型调用 | 4万元 |
| 差旅与专项审查 | 3万元 |
| 上述直接及归集成本合计 | 58万元 |
| 按此口径的剩余金额 | 22万元 |

22除以80，得到27.5%。到这里，经营者可以说“按目前列明口径，项目还有27.5%的剩余”，却还不能直接称其为净利润。前期获客、共享研发、行政管理、资金占用，以及其他尚未列入的支出，仍需在相应账里处理。

现在发生一次范围变化：客户增加一种设备类型，需要一名工程师再工作20天，同时模型与云费用多出2万元。若原合同不变，新增投入是6万元人员成本加2万元资源成本。项目成本升至66万元，剩余14万元，相应比例降到17.5%。

界面上可能只多了一个选项，经营结果已经改变。工程师是否足够努力，无法解释这8万元。它来自交付范围与资源投入的变化，需要被识别、记录和决定。

回到未发生范围变化的基线：另有尚未计入的售前试验和获客投入12万元，以及按事先约定分配依据归入的共享设施、行政费用15万元。这里的27万元明确排除了前表人员、专用资源和支援工作，不能让同一张账单或同一批工时再出现一次。

| 口径对照 | 未变更范围 | 已增加设备类型 |
| --- | --- | --- |
| 收入 | 80万元 | 80万元 |
| 项目直接及归集成本 | 58万元 | 66万元 |
| 此前未计入的获客及共享费用 | 27万元 | 27万元 |
| 宽口径成本合计 | 85万元 | 93万元 |
| 按这一较宽口径的剩余 | -5万元 | -13万元 |

两列都能成立，因为它们回答不同范围下的同一个问题。范围变更不会在扩大核算口径时消失。这些仍是教学经营账，没有覆盖税务、资金和全部公司级项目，不称为法定净利润。

真实项目不需要先建复杂系统，可以先让每笔投入带着日期、工作对象、投入量、归属和确认人。例如，一位产品工程师花两天修复本客户必须使用的接口，由项目负责人确认进入前表6万元支援项；若另外三天由产品负责人批准开发其他客户也可使用的通用能力，这三天才单列为产品投资。不能把五天都报给交付，再把三天从研发分摊回来。

持续维护应由运行负责人确认服务期与资源；尚未发生的后续支持列为未来预算，别混成已发生成本。共享费用则先剔除已直接归属的部分，再按项目事前选定的使用量、人日或其他合理依据分配，保留未分配余额。方法可以不同，但同一周期不要为了改善某张项目表而反复改变方法。

这样，若管理者接受阶段性亏损以换取可复用能力，就必须明确能力是什么、由谁维护、何时检查其他人是否使用，而不只是把费用改一个部门名字。

账算清楚以后，讨论反而可以更开放。某个首创项目可以获得战略预算，一个高度重复的成熟项目则应被要求稳定交付。把它们都塞进同一个平均毛利率，管理者既看不见探索的价值，也看不见重复劳动的成本。

## 客户的“节省时间”如何变成价值

现在把同一份80万元合同交到客户财务负责人手里。假定一期上线后观察12个月，每月处理一万件工作，每件少做六分钟旧步骤，却新增两分钟复核。净释放时间是每月约667小时，全年8000小时。这不是自动减少的工资账单：人员仍可能在岗，时间也可能转去处理积压。

客户为这份合同支付80万元，另有内部准备和培训投入8万元，其中6万元是既有人员被占用的工时，2万元是新增培训支出。上线后12个月另付12万元运行和支持费，明确不含供应商一期项目已经列出的4万元部署期资源。于是客户首期经济投入为100万元，新增现金支出为94万元；6万元内部工时有机会成本，却不在本例中产生新增工资付款。

怎样让时间收益进入这张账？假设观察记录显示，释放时间中的每月400小时替代了原本确会购买、并已停止采购的外包工作，外包单价200元/小时；剩下约267小时用于消化积压，没有记现金收益。全年可核的少支出为96万元。不是8000小时全部乘单价，也没有把积压缩短另算一次收入。

| 同一合同，首期投入加上线后12个月 | 金额或结果 |
| --- | --- |
| 合同80＋内部准备8＋运行支持12 | 经济投入100万元 |
| 扣掉未新增付款的内部工时6 | 新增现金支出94万元 |
| 确认少采购外包400小时/月×200元×12月 | 少支出96万元 |
| 少支出减经济投入 | -4万元 |
| 少支出减新增现金支出 | 2万元 |
| 仍待业务评价的改善 | 每月约267小时转去处理积压；没有折成收入 |

这组教学观察允许两句话同时成立：客户的新增现金收支略有改善，首期经济投入尚未全部收回。供应商前表的宽口径剩余则为负5万元。双方都不能用另一方的数字宣布自己的项目盈利。是否继续，要看积压改善是否值得、后续成本是否下降，以及服务质量有没有受损。

再动一个条件，结论就可能反转。若实际停止采购的外包只有每月300小时，全年少支出降为72万元，客户经济差额为负28万元、现金差额为负22万元；若要覆盖100万元首期经济投入，按这个外包单价，每月需真正少采购约417小时。417是本例的计算结果，不是FDE项目应达到的行业门槛。

这也是研究结果需要保留原口径的原因。《Generative AI at Work》的2024年修订摘要使用5172名客服人员的数据，报告每小时解决问题数平均提升15%，同时指出不同经验组的变化不同。这个结果不能直接变成“采用 AI 后利润提高15%”，更不能变成 FDE 模式的普遍投资回报。[^2]

对 FDE 来说，重要工作是帮助客户把测量放回流程。原来一件工作如何开始、何时算完成、哪些异常被排除、是否转给别人处理，都要尽量保持可比较。否则团队可能只是把困难环节移到统计范围之外。

## 成本降下来，收益会留在谁手里

前面的账还默认了一件事：完成同样工作的价格没有变。可一项技术一旦容易获得，客户会重新议价，竞争者也可能降低报价。工程团队创造了效率，经营主体能留住多少，是下一道问题。

沿用本章的教学合同，只比较直接项目剩余。原报价80万元，直接成本58万元，剩余22万元。若工具进步把同口径成本降到48万元，在报价不变时剩余变为32万元；但下一份相同范围合同若只能卖70万元，剩余又回到22万元。交付确实便宜了，增加的10万元利益却通过价格让给了客户。这几项是假定条件，不是市场降价预测；直接剩余也仍未扣除前述获客与公共投入。

客户同样需要作这个检查。少付外包费会改善当前现金收支；如果客户自己的产品也随竞争降价，原先测得的少支出未必全部留下成为利润。反过来，等待缩短、服务更稳定，可能帮助客户获得更多订单。哪一种发生，需要看实际价格、销量和服务质量，不能只把省下的工时乘一次单价。

因此，本书建议把收益表再加一列：**谁能在下一次交易中重新定价？** 供应商、客户和客户的客户，可能依次拿走不同部分。FDE不能决定整条产业链的利润，却可以把承诺写实：这次改善的是处理能力、现金支出，还是已经观察到的经营收益。若还没有跨过续约或旺季，就把价值能否保留留待下一轮检查。

## 模型费用很显眼，隐蔽成本更值得找

调用账单容易被注意，因为它定期出现。但在项目初期，查权限、解释数据、确认需求和处理例外也可能消耗大量资源。它们不一定都应被消灭，有些正是理解客户所需的工作。经营管理要区分：哪些是一次性的学习成本，哪些每增加一位客户都会再发生，哪些随着使用量增长持续增加。

一次性学习成本能否复用，要靠后续项目证明。一个连接器——让两个系统交换资料的软件——在第二位客户那里仍然需要大改，说明原先识别的共性可能不足。按使用量增长的成本则需要对应容量和定价。如果收入固定，模型调用、人工复核和支持请求却随交易量上升，成功采用也可能让供应商的利润变差。

还有一种成本来自承诺本身。为关键系统提供快速响应，就要保留有人可调动的能力。人员暂时没有处理工单，不表示这项承诺免费。若把所有人排满再卖出响应承诺，组织就只能在故障到来时打断其他客户。

客户内部投入同样应在立项时被看见。业务专家需要提供例子，数据负责人需要整理字段，一线人员需要学习新步骤。把这些成本排除，供应商的方案会显得便宜，客户却可能因无力配合而迟迟无法得到成果。

## 为什么第二个客户最有解释力

第一个项目说明团队能不能把某件事做成。第二个项目开始说明：前一次的投入究竟留下了什么。

第二次交付首先应该回到前面的投入表。假设前一期150个工程人日中的数据接入工作，在第二位客户处确实少了20人日，按原教学单价看，少发生6万元投入。但共享工具若又需要10个人日维护，就不能把6万元全部当作净收益。应当把第二项目实际减少的工作与新增长期维护分开列，并让产品负责人确认公共投入的承担范围。

上一项目已经支付过的开发成本，复盘总投入时仍然存在；第二项目没有再次发生，就不能再把它当成新现金支出。反过来，未来持续维护也不能因为“代码已经有了”而归零。哪些能力值得抽成产品，留给C27《每个客户都不同，产品怎样成长》。

英国政府的数字采购指导要求在合同结束前考虑知识、数据和接任安排。虽然它面对的是公共采购，这种全生命周期视角也提醒商业项目：移交与退出有成本，不能因为不发生在首次上线之前就从估算中消失。[^3]

## 定价应当对应谁承担哪种不确定性

本书不提供一个适用于所有企业的报价公式。我们可以比较几种选择如何改变行为。

按时间收费，容易看清投入，但客户可能担心解决问题越慢、账单越大。固定范围收费，给预算带来确定性，却要求双方认真管理范围变化。按软件订阅加实施费用，能将持续产品能力与一次性接入分开，但要解释哪些支持已经包含、哪些另行发生。按结果付费看起来最贴近价值，前提是结果可以测量，而且供应商对关键变量有足够影响力。

如果项目目标是减少某项业务损失，而价格、客户政策、市场环境和内部执行都能改变损失，仅按结果结算就可能引发长期争执。问题不在于这种模式天然好坏，而在于计量范围、影响能力和风险承担是否匹配。

Sierra在2024年12月的定价说明中，把客服问题解决、挽留取消等列为可约定的结果；同一篇文章也承认，迎宾、路由一类交互可能更适合按会话计费的混合方式。[^4] 这比一句“以后都按效果收费”更有解释力：有些任务的终点可以清楚计量，有些任务只负责把工作交给下一环。

把它放进一份教学合同，双方至少需要共同判断一次账单：机器人说“已解决”后，客户当天又来追问，算一件还是两件？先由AI收集材料、再由人工处理，分别如何付费？挽留成功是否要等退款窗口结束？这些约定决定谁承担未完成、重复联系和后续反悔的费用。还要分清验收条件与计价方式：固定总价的项目也可以约定达标才付款；按已确认结果的数量结算时，每项结果的单价可以固定，变化的是总费用。

埃森哲在2026财年第一季度的业绩演示中，恰好把两者分开：公司称，2025财年约60%的工作采用固定价格，而以实际实现的结果为基础的商业安排仍只占很小部分。[^5] 所以，看见一家服务商增加固定价格合同，不能直接写成它已经大规模按业务结果收费。双方可能只是重新分配了超时、返工和工具提效的收益与风险，客户的经营结果未必成为结算单位。

较务实的办法，是先把不确定性拆开。探索阶段允许有限的学习预算，达到明确证据后再扩大范围；已经稳定的功能采用更确定的交付与维护约定。这样可以防止一种不舒服的情况：供应商承诺了无法控制的结果，客户则以为所有后续变化早已包含在价格里。

## 从今天起，继续投入是否值得

项目从开始算亏了多少，与今天应选哪条路，是两个问题。过去已经发生且无法收回的投入，需要在复盘时承认；决定下一步时，还要比较各方案从现在起会带来什么。

继续使用增加设备类型后的教学项目，原计划收入80万元、上述较宽口径成本93万元。假设在一个决策时点，已有60万元收入对应的工作完成，成本中73万元已经发生；余下收入20万元，要完成剩余交付才能获得。下表比较经营投入，已发生项均不可收回；它没有说明款项何时到账，现金另列在后。

| 从当前时点比较 | 以后可取得的收入 | 以后还需投入 | 以后的收入减投入 |
| --- | --- | --- | --- |
| 完成当前全部约定 | 20万元 | 20万元 | 0万元 |
| 客户同意缩小范围并重签余款 | 12万元 | 8万元 | 4万元 |
| 双方同意终止并完成必要移交 | 0万元 | 3万元 | -3万元 |

完成剩余约定的未来收入与投入相抵，协议退出则净付出3万元；从项目开始算，前者剩余为负13万元，后者为负16万元。因此“全口径亏损”本身不足以推出“马上停止”。第二条路更有吸引力，却以客户同意调整合同为前提；供应商不能单方面缩减承诺来创造利润。

这张表还没有替管理者作完决定。要确认余款是否可靠、人员被占用会错过什么工作，以及新的投入能否带来可验证的产品能力。如果等待客户批准，每周还需继续付费，就要把等待也计入；若某项支出即使退出也必须承担，不能假装停止后便归零。

## 钱够不够周转，是另一道关

回到未增加设备类型的基线，给80万元合同补上付款时间。下表支付共70万元，由直接成本58万元加获客12万元组成。另15万元共享分摊没有逐项对应到本项目的新增现金，暂不塞进现金表里；它仍留在85万元的宽口径成本账中。月份相对签约安排，负一月表示签约前。

| 月份 | 客户付给供应商 | 供应商上述现金支出 | 累计项目现金净额 |
| --- | --- | --- | --- |
| -1 | 0 | 12万元获客支出 | -12万元 |
| 1 | 24万元 | 20万元 | -8万元 |
| 2 | 36万元 | 25万元 | 3万元 |
| 3 | 0 | 13万元 | -10万元 |
| 4 | 20万元 | 0 | 10万元 |

期末现金净额10万元，不能覆盖或否定成本账里的负5万元，两张表相差的是15万元分摊口径；公司仍要为共享资源付款，只是其支付时间和增量未在此表展开。按这些月末余额，项目最深的缺口为12万元；月内收支先后未列出，实际备款还要检查具体支付日期。若第二月的36万元推迟到第四月，第三月末缺口就变为46万元，期末仍为10万元。项目金额没有变，公司却需要多准备34万元周转。

另一种敏感性来自返工和调用量。以58万元直接及归集成本为基线，再增加10个工程人日，宽口径剩余从负5万元变为负8万元。若部署期4万元资源费中1万元固定、3万元随调用量变化，调用量翻倍且其他项不变，剩余也变为负8万元；两件事同时发生则为负11万元。这里采用线性变化只为暴露假设，真实用量可能跨过容量档位，不能照搬倍数。

[80万元合同工作账](../appendix/toolkit/engineering/C26-economics/README.md)把双方口径、付款表、敏感性和继续／缩小／退出三条路放进可下载CSV与JSON。先用原始数字复算，再改一个条件。较有价值的讨论往往不是争执一个投资回报率，而是指出：哪笔成本归谁、哪个收益已经实现、哪一笔钱到得太晚。

## 什么样的学习值得再给预算

假设两个项目都亏损。一个发现了许多客户共同遇到的限制，产品团队已经接手，后续部署可以验证改进；另一个不断增加专用分支，客户离开原团队便无法运行。两者的本期报表可能相近，未来路径却不同。

但前一种也需要证据，不能靠一段动听的“战略价值”解释无限续命。值得继续投入的条件应具体：哪项能力在什么时间进入受维护产品，谁是下一位明确使用者，怎样观察投入是否下降。如果这些条件连续落空，团队需要重新估计，而不是在每次复盘中重复愿景。

停止一个项目也不必等到所有可能性都被试完。当核心数据无法合法或稳定取得、客户没有能力配合、结果无法验收，或者解决成本远高于可获得价值时，缩小范围或退出可能是负责任的决定。退出所需的服务连续性和资料移交仍要认真完成。

从这个角度看，FDE 的经营能力并不只是把复杂项目卖出高价。它还包括把学习投入和重复成本分清，把客户价值和供应商收入分清，让每一次扩大承诺都有相应证据。

下一次有人展示一个成功项目时，可以先看成果，再顺着成果追问：客户真正改变了什么，投入来自哪些人，后续由谁承担，下一位客户能复用多少。问到这里，你看到的才开始是一门生意。
