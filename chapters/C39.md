# 法国：本地模型与业务机构怎样共建

选择一家本地模型企业，并不会自动解决数据、工作流程和采用问题。法国的客户材料让这个区别更清楚：业务机构可以自己提出问题、组织试验，同时借助供应商把新的能力接进已有系统。

## France Travail：员工提出的问题怎样进入产品

法国公共就业服务机构 France Travail 的材料，让我们看到客户内部如何组织变化。其2025年6月10日公告称，ChatFT 自2024年11月起向全体员工开放，可直接使用，也可嵌入顾问业务工具。公告还区分了 Neo 的阶段：2024年10月在少数机构及志愿用户中试验，2025年4月15日起逐步扩大部署。Neo 让顾问用自然语言访问机构信息系统。[^1]

自然语言，就是工作人员用平常说话的方式提出请求，不必先记住系统里的每个菜单或查询写法。它让界面更容易接近人，但后台仍然需要知道人是谁、允许查看什么、哪些记录属于同一位服务对象。界面变简单，不能把这些责任一起简化掉。

同一公告称，MatchFT 和 Neo 当时已经使用 Mistral 技术，同时把双方合作签署列为6月11日的安排。[^1] 这提醒我们，公开合作签署日不一定是工程工作的第一天；应用开放日，也不一定是所有员工真正采用的那一天。把这些日期压成一条“签约后立即全面成功”的故事，反而看不见项目怎样成长。

Mistral 的客户页将相关应用描述为帮助顾问汇总求职者资料，以及通过内部问答查找劳动规则等信息。[^2] 这是供应商对用途的说明，没有证明模型独自完成就业服务，更没有证明某项结果是由 FDE 这一岗位造成的。

France Travail 在2025年 VivaTech 活动回顾中，则介绍了其内部孵化方法：从一位员工提出的工作困难开始，小范围试验，再视顾问使用情况决定扩展。[^3] 这与“买来一个现成工具，通知所有人使用”的路径不同。业务使用者不仅参与最后验收，也可能是问题最初的提出者。

这条客户侧记录说明，供应商并非唯一的问题发现者。顾问的工作困难可以先进入内部试验，再由机构决定是否扩展；外部伙伴需要接入这套选择过程。对于 FDE，重要的不是自己发起了多少原型，而是能够解决内部团队已经看见、却还无法独立处理的哪一个工程缺口。

不过，员工提出需求与公共服务改善仍是两个判断。材料显示了孵化入口和部署阶段，没有给出足以分离各方贡献的长期结果。我们可以比较问题从哪里来，却不能据此认定法国机构比美国或英国更善于采用 AI。

## 一家集团的长期合作，不等于一种通用工作

CMA CGM在2025年度回顾中说明，集团于2025年4月与Mistral AI建立五年战略合作，以1亿欧元投入支持航运、物流与媒体业务的定制AI整合。这个数代表披露的合作投入，不能拆成FDE工资，也不能当作已经实现的收益。[^4]

它为France Travail之外提供了另一个客户位置：横跨不同业务的企业集团，能够通过较长期的合作组织技术投入。优势可能是减少每个项目重新寻找伙伴的成本；风险则是把集团层面的统一承诺，误读为每个业务的需求已经相同。前者是可以检验的经营推断，公开回顾没有给出逐项目成本来证明它已实现。

航运信息、仓库操作和媒体内容即使都能使用同一模型，也不会因此有同一套“完成”标准。试想一项系统生成船期说明，另一项系统整理新闻素材，这是教学比较：前者需要确认航次与时间状态，后者还须确认材料出处与编辑责任。复用模型或技术伙伴，只解决了部分供给条件，不能把一种业务的授权搬到另一种业务。

## BNP Paribas：一份合作公告里，也有不同的完成阶段

2026年9月24日，BNP Paribas 与 Google Cloud 宣布五年合作。公告同时说明：Nickel 业务的客服助手 Nickel Assist 已帮助200名客户顾问依据内部流程查找答案；把 Gemini 接入企业与机构银行部门既有的内部助手 LLM@CIB，以及用 Agent 准备企业信用备忘录，仍属后续安排。[^5] 已有助手可向逾65,000名员工提供，并不表示新模型已覆盖这些人；200名顾问的范围也不是200人持续活跃的证明。

联合材料还给出具体治理方向：某些类别的数据不存入公有云，每个 Agent 经认证后，只取得任务所需资源的权限，系统连接与交互受监控。这不是“只使用本地模型”的选择，而是在多云、多模型之间按业务需要决定控制程度。

对现场交付，银行先要划清哪种资料可以进入哪种环境，再测试顾问是否能按适用流程找到答案。后续信用分析不能直接沿用客服助手的授权。该案例没有明确FDE职衔，也没有证明这份新协议已经带来全行经营成果；它补充的是客户如何在已有能力上安排下一阶段的证据。

## 怎样理解本地合作，而不把它写成文化标签

France Travail与CMA CGM的材料都出现法国客户和Mistral，但由此得不出“法国企业只买本土模型”的结论。可核查的是具体合作及其范围；还需要另查的，是每个项目为何选这家伙伴、比较过哪些替代、如何部署，以及客户是否能迁移。没有这些资料，不能把国家认同当作已证明的采购因果。

本地合作真正值得进一步检查的内容，可以落到三项工作：业务术语能否由本机构人员纠正；模型、应用和资料分别由谁维护；更换技术伙伴时，知识与应用是否仍能使用。这些也适用于跨国供应商，不能只凭总部所在地回答。

本章所见的工作理念，是让业务知识的提出者保有作用，并把模型能力接到已有的组织选择中。France Travail的员工孵化说明问题并非总由供应商发现；CMA CGM的集团合作则要求把总体投入继续拆成业务能够验收的项目。两者都不是购买一个名称之后等待转型自动发生。

## 先选业务问题，再选择共同建设的范围

设想一家机构准备为顾问增加自然语言查询，这是教学安排。业务负责人先列出哪几类问题可以读取已有信息、哪几类涉及进一步解释、哪几类必须改变记录。供应商演示相同界面，三类请求背后的权限与错误后果却不同。

首期可以只开放可核查的读取任务，并让顾问指出缺失或歧义。若发现难点实际在源头资料，团队先调整数据，而非继续增加模型；若标准产品已覆盖任务，长期伙伴关系也不应成为额外定制的理由。相应的自建、采购和合同选择见[甲方选择](C33.md)与[合同与价格](C36.md)。

法国材料能说明客户如何参与共建，不能证明整个国家采用了同一种FDE组织。把这一边界保留下来，才更容易发现下一家机构真正相同的困难，以及必须重新选择的部分。
