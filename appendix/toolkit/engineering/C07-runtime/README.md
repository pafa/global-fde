# C07：一台洗衣机为什么没有变成两台

这是一份完整填好的教学轨迹，不是 OTTO 或任何客户的代码。它只检查需求改变、回执丢失、重试和进程恢复之间的关系。时间是示意，不能用来评价真实性能。

先看 [8 步记录](trace.csv)，再看 [请求与回执](requests-and-receipts.json)。非技术读者只需核对三件事：当前条件是55厘米；最终商品宽54厘米；最终数量始终为1。技术读者再核对意图编号、内容摘要与购物车版本。

## 练习与示范判断

1. 遮住记录的 next_action 列，填写 [空表](trace-blank.csv)。第4步没有回音，应记结果待核实，不能报告失败，也不能再发一个新的动作号。
2. 第5步把 A1 改成 A2。示范判断：后端不能据此识别同一次意图，可能多加一台。修复需要沿用已保存的 A1，不是删掉重试功能。
3. 保留 A1 却把 quantity 改为2。示范判断：与原内容不一致，应报冲突；顾客若确实想再增加，需要新的明确确认与新意图号。
4. 第6步返回的商品便宜很多，能否推荐？不能直接推荐，它不满足当前55厘米条件；可以重新按v2查询，不应自行恢复旧条件。
5. 如果第7步回执有R1、购物车读不到，能否宣布已经核实？不能；保留不确定并升级排查，不重放写入。相反，若核对结果一致，可以恢复已确认进度。

判据是这些状态与动作是否一致，不以“全程无错误”得分。此包没有实现库存保留、支付或权限；用于真实项目前须另建相应控制与测试。输入、编号和商品均为合成数据。
